# სინთეზური მაგალითები

ეს ფაილები მხოლოდ [მე-3 ნაწილის დამოუკიდებელი ინციდენტის](../ASSIGNMENT.md#ნაწილი-3-დამოუკიდებელი-პრაქტიკული-ინციდენტი) ილუსტრაციაა. დამატებითი დავალება ან production წვდომა საჭირო არაა. მაგალითები სრულად გამოგონილია და არ წარმოადგენს რეალური სისტემიდან ექსპორტს.

- `orders-sample.sql` შეიცავს 7 გამოგონილ ჩანაწერს, ორ tenant-ს და თავდაპირველ query-ს მცირე, ლოკალურ table variable-ზე. `@Orders` მხოლოდ `dbo.Orders`-ის რამდენიმე სვეტის ილუსტრაციაა. მაგალითი არ ცვლის დავალებაში მოცემულ 8 მილიონ ჩანაწერს, ინდექსს ან tenant/day skew-ს და არ გამოდგება performance-ის ან locking-ის შესამოწმებლად. მისი გაშვება სავალდებულო არაა; წაკითხვა საკმარისია. SQL არ ქმნის მუდმივ ობიექტებს და არ უკავშირდება გარე სისტემებს.
- `incident.log` ხელოვნურად აერთიანებს რამდენიმე log-ისა და read-only snapshot-ის ფრაგმენტს. ეს არ ნიშნავს, რომ სისტემას უკვე აქვს ცენტრალიზებული logging. Request IDs, order IDs და tenant IDs მხოლოდ ამ მაგალითებისთვისაა შერჩეული; ფაილი სრული trace ან actual execution plan არაა.

მაგალითისთვის არჩეული სამშაბათია **2026-10-06**; ყველა timestamp UTC-შია. თარიღი მხოლოდ fixtures-ს ეკუთვნის და day 60 სცენარის თარიღს არ განსაზღვრავს. `CreatedAt` არის UTC `datetime2`, `@Day` — UTC კალენდარული დღე. მცირე ცხრილში ყველა ჩანაწერის შექმნის დრო 10:12 snapshot-ს წინ უსწრებს.

Snapshot აღებულია 10:12:00-ზე: session 72-ის transaction დაიწყო 10:09:55-ზე — 125 წამით ადრე; session 84-ის elapsed არის 21 წამი, session 91-ის — 17 წამი. Partner timeout-ის ფრაგმენტები 5-წუთიან ციკლებს აჩვენებს, თითოეული 120-წამიანი ლოდინით. ისინი სრული transaction lifecycle-ის მტკიცებულება არაა.

Logs-ში მითითებული p95, timeout-ის წილი, CPU და disk latency დავალებიდან აღებული სინთეზური მაჩვენებლებია და ამ რამდენიმე სტრიქონიდან არ გამოითვლება. Backup jobs-ის მწვანე სტატუსი აქ მხოლოდ მოცემული დაკვირვებაა. ამ ინციდენტში PIT restore გამოუცდელია; მე-2 ნაწილის rehearsal-ის შედეგები აქ არ გამოიყენება.
